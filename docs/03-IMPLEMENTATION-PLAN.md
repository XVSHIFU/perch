# 03 实施计划

## 执行原则与当前基线

按用户 2026-09-25 的要求，前期 P0–P7 视为开发完成，当前开发范围为 P8。保留既有源码、界面和真实能力，在现有工程上逐步扩展，不重新搭建项目，也不要求重新完成前期全部验证。

本项目为个人开发者的开源研究与开发项目。优先按照计划完成可用功能；不预设大用户体量，不增加与当前需求无关的工程体系。只做本次改动所需的局部检查，复用已有验证结果，避免重复测试和模型调用。文档保留本计划、必要使用说明与已有进展记录即可。

P0–P7 以下文字为此前的实施与验证记录，其中“待验收”“未运行”和人日估算保留其历史含义，不覆盖本轮的阶段完成认定，也不作为进入 P8 的新增门槛。P8 的计划状态不等于代码已实现；本轮只补充计划。

构建与局部检查通过；新版窗口、托盘、默认浏览器与退出清理由用户实测确认。证据与未验证范围见 PROGRESS.md。

验收：900×600 与 1180×780 均可操作；真实窗口和 demo 生命周期完成。环境不足则明确记录哪项没跑，继续可完成的静态工作，不伪造通过。

### P8.0 — 调研结论与整合边界

以下“上游事实”为本轮资料核查结果，“采用方式”为栖点的设计决定；资料索引见本阶段末尾。文档与默认分支会变化，开发时只在真正接入某个来源时核对其清单格式和目标版本，不重新做一轮全生态调研。

| 参考对象 | 上游事实 / 可借鉴内容 | 栖点采用方式 |
| --- | --- | --- |
| PCL / PCL-CE、Prism Launcher | 启动器围绕版本、实例与整合包组织操作；Prism 提供选择版本、整合包及导入的建实例入口。[S01–S03] | 保留“先选用途或版本，再创建实例”的流程；借鉴交互，不在 P8 移植启动器底层或换掉 Tauri。 |
| GitHub Releases、Tags、npm | Releases 列表不包含所有普通 Git 标签；npm 发布版本也不能仅由 GitHub Release 推断。[S04–S06] | 分别采集发布元数据与可安装工件，关联显示，避免“只有 Release 的才算版本”。 |
| DSH 官方插件机制 | 包通过 `dsh.bundle` 声明装配内容，profile 的 bundle 顺序会影响配置覆盖。[S07–S08] | 由 DSH 适配器处理装配、顺序与生效检查，不能把普通依赖安装成功当作插件已启用。 |
| Pi 包与 Pi Web | Pi 包可同时含扩展、Skills、提示词和主题；Pi Web 是独立工作台，需与对应 Pi 依赖匹配。[S09–S11] | 市场展示包内资源，允许按支持能力选择；继续锁定“引擎 + Web + 扩展”的实际组合。 |
| Pi 扩展运行模式 | Pi 的终端 UI 扩展能力与 RPC 等运行方式存在差异。[S12] | 将“支持 Pi”与“能在当前 Pi Web 使用”分开判断，尤其不承诺终端自定义组件在网页可见。 |
| DSH 创意工坊 | 网站涵盖插件、皮肤、宠物和预设；仓库公开构建数据来源及子模块映射。[S13–S15] | 优先读取仓库公开清单及其固定提交，按资源类型适配；无需先搭建网页爬虫平台。 |
| Agent Skills、skills.sh | Skill 有目录结构与元数据约定；skills.sh 可用于发现资源，其公开 API 文档另有认证条件。[S16–S18] | 导入完整 Skill 目录并保留来源；发现入口与直接安装能力分开，不把网页可访问等同于 API 可匿名调用。 |
| Modrinth 依赖模型 | 依赖可区分必需、可选、冲突与已内嵌。[S19] | 在安装清单里表达这些关系，让用户知道“会一起安装什么”和“为什么装不了”。不引入 Minecraft 专用格式。 |

补充：本轮访问 `Congser/PCL-DSH` 未取得可核查的仓库内容，仍保留为用户提供的参考，不据此断言其实现方式，也不让它成为 P8 的依赖。[S23]

**沿用的基础能力**：P2 的持久化与模型连接，P3/P4 的安装器、实例隔离和进程管理，P5 的扩展操作与整合包入口，P6 的锁定、快照、克隆及恢复，P7 的 Windows 桌面外壳。P8 增加目录来源、版本解析和组合编辑，复用同一条安装事务链。

**本轮不扩展的范围**：多用户账号、收费交易、云同步、社区投稿审核平台、远程实例集群、内嵌浏览器替换、多操作系统发行和全面自动更新服务。MCP 可作为资源说明或已支持插件的依赖出现，不顺带新建通用 MCP 管理平台。

### P8.1 — DSH / Pi 全版本目录与版本选择

#### 1. 用户入口与默认行为

- “新建实例”提供“从整合包创建”和“选择引擎版本”两个入口；空白实例也必须解析为固定组合。
- 实例详情增加“版本与组件”，并列显示引擎、Web 工作台、运行时和已安装扩展。当前使用与候选版本不能混在一起。
- 默认推荐现有已验证组合；正式版为默认筛选，可打开预览版筛选并搜索历史版本。历史列表分页加载，不人为只保留最近若干个版本。
- 选定版本后展示发行说明、来源、运行条件和兼容结果，再生成安装计划。已有实例优先提供“克隆并试用此版本”，其次才是原实例切换。

#### 2. 版本来源与完整性

| 组件 | 首批目录来源 | 处理方式 |
| --- | --- | --- |
| DSH | `deepseek-ai/deepseek-harness` 的 Releases / Tags，以及官方 npm 包 `@deepseek-ai/dsh` 的发布记录 | npm 版本对应可安装包，仓库发行记录补充说明；只有标签而没有可用工件的版本仍可查看，但说明不能直接安装的原因。 |
| Pi | 官方 Pi 仓库、已确认的官方 npm 包发布记录 | 保留现有安装所用的旧来源映射；新目录识别当前来源和历史别名，不把仓库迁移当成两个无关引擎。 |
| Pi Web | `agegr/pi-web` 发行记录、包元数据及依赖约束 | 与 Pi 版本一起解析；不能只替换独立 CLI 而保留不匹配的 Web 依赖。 |
| DSH Web | 当前 DSH 发行物提供的 Web 能力 | 随引擎发布时表示为“随引擎”，不人为生成独立 Web 版本；确实独立发布的组件再单独锁定。 |

本轮核查时，Pi 文档入口已指向 `earendil-works/pi`，包文档使用 `@earendil-works/pi-coding-agent`；旧记录中的 `badlogic/pi-mono` 和 `@mariozechner/pi-coding-agent` 需要保留为历史来源。[S09–S11] 开发时核对目标包的发布者、仓库与依赖关系，添加显式映射；**不批量改名、不自动迁移已有实例、不直接改旧锁文件**。

“全版本”的范围是：配置来源能够公开取得的正式版、预览版及历史标签，不包含私有草稿、已不可取得的制品或臆造的版本。目录完整性与运行支持是两件事；遇到限流、分页未完成、来源失效，应显示“尚未同步完整”，不能把不完整结果写成全量目录。

目录应保存：来源标识、原始版本、发布时间、发布通道、发行说明链接、标签/提交、工件地址、上游完整性值、声明的运行条件和最后同步时间。Git 分支与 npm dist-tag 可用于发现，但进入实例 lock 前必须解析成精确版本/提交。

#### 3. 兼容性与适配策略

- 兼容判定覆盖 Windows 架构、运行时、引擎、Web、扩展加载方式以及模型协议需求。继续沿用当前 Windows x64 运行时基线；新版本需要不同运行时时，复用工件管理安装受管版本，或明确标记暂不支持，不能覆盖全局 Node。
- 先做“有证据的版本范围规则 + 少量例外”，为明确改变配置/启动协议的版本增加适配配置；不要为每个历史版本复制一套完整适配器。
- 分开保存上游声明与本机验证结果，不能把 `engines` 字段、安装成功或 GitHub 热度当成完整兼容证据。

| 对用户显示 | 含义与操作 |
| --- | --- |
| 已验证组合 | 有对应平台与组合的检查记录，可正常创建。原有固定组合继续属于此类。 |
| 符合声明，尚未验证 | 工件、启动映射与约束可解析，但缺少本机组合记录；可选择克隆试用，不自动升级现有实例。 |
| 不兼容 | 存在明确冲突；显示冲突组件和可选版本，阻止应用该计划。 |
| 暂未适配 / 缺少工件 | 信息不足以生成可靠安装计划；保留详情和来源入口，不伪造安装按钮成功。 |

预览版、正式版属于发行通道，不替代上表；“已缓存”“已安装”“下载中”属于工件/任务状态，也不替代兼容结果。未知条目不会因一次进程启动就自动成为全局推荐组合。

#### 4. 安装、切换与回退

1. 解析精确组合和依赖，展示与当前实例的差异、需下载内容、配置变化及是否需要重启。
2. 复用 P6 创建快照和 P3 安装暂存区，校验下载完整性，再运行适配器所需的局部健康检查。
3. 原实例切换前停止目标实例；成功后激活新 revision，失败保留原 revision 和可解释日志。其他实例继续运行。
4. 区分程序版本回退与会话数据回退：新引擎可能迁移数据格式。没有明确向后兼容依据时，使用切换前快照或新数据副本，不能让旧引擎直接改写新格式数据。恢复不覆盖用户项目代码。
5. 保留本机 `connectionId` 并重新判断目标引擎是否支持该连接；不要求重新输入 Key，也不擅自更换服务商。

验收：能浏览双引擎历史与预览条目；完成一次非默认版本的真实创建/克隆试用；不兼容项有明确原因；失败后原实例仍能打开。无需逐一安装全部历史版本。

### P8.2 — 统一扩展市场与来源管理

#### 1. 信息结构

统一入口叫“扩展”，提供“发现 / 已安装 / 来源”。发现页以搜索、引擎和类型筛选为主；详情展示适用实例、版本、来源、依赖和安装动作。已安装页始终明确当前实例，避免用户误以为所有实例共用同一套插件。

资源类型包括：DSH 插件、Pi 扩展、Skills、提示词、主题/皮肤、Agent 预设，以及宿主支持的宠物资源。类型不等于生态，一个包也不等于一种资源。

- 目录对象分为“可下载的包”和“包内资源”。Pi 包可包含多个类型；一个仓库也可能包含多个独立 Skill 或子包。
- 显示包内清单，按上游能力支持选择性启用；只有必须整体安装时才作为整体处理，并提前说明。
- 对主题、宠物、预设保留宿主要求。例如需要特定 DSH 皮肤插件的资源，先解析其依赖；未实现对应加载器时只提供浏览/来源入口，不能承诺对任意 DSH Web 生效。
- Pi 资源标明适用界面：Web、终端、两者或未知。仅终端 UI 功能不包装成 Pi Web 的可用功能。

#### 2. 首批来源与接入优先级

| 来源 | 纳入的内容 | 第一轮实现 |
| --- | --- | --- |
| 已有 P5 内置目录 | 已验证插件、Skills 与固定组合 | 原样迁入统一目录结构，作为随应用提供的可用基础数据。 |
| GitHub `dsh-plugin` topic + 人工精选仓库 | DSH 社区插件发现 | 读取仓库元数据与明确的包声明，关联 npm/Release 工件；topic 只是发现线索，不是兼容认证。[S20] |
| `dsh-market.com` / `zhu1090093659/dsh-web` | 插件、皮肤、宠物、预设 | 优先接入仓库中的公开数据清单；锁定对应提交和子模块版本，不执行网站构建脚本来获取目录。[S13–S15] |
| Pi 官方包目录 / npm `pi-package` | Pi 包及包内多类资源 | 用官方目录发现，用 npm/Git 包元数据确认版本、内容与工件；不假定网页存在未公开 JSON API。[S10–S11] |

DSH 创意工坊仓库的 `market-inputs.lock.json` 描述了 skins、pet、community、presets 的数据入口，并通过 Git 子模块固定来源。[S15] 适配时跟随文件中声明的映射和固定提交，避免把内容目录硬编码成永远不变的路径。README 提到的 `skin.json`、`pet.json`、`community.json` 可作为解析入口线索，实际字段以选定提交为准。

来源接入顺序：已有目录 → Pi 包目录与 DSH 精选/topic → DSH 创意工坊清单 → 通用 Skill 仓库 → 更多手动来源。一个网站不可用只影响该来源，不阻塞已有实例与其他市场内容。

#### 3. 采集与缓存实现

读取优先级为：公开结构化 API / 清单 → 明确仓库路径中的元数据 → 针对已配置网站的轻量页面解析 → 手动粘贴来源。不要建立任意网站爬虫、执行仓库脚本或通过 LLM 推测安装命令。

- Rust 侧完成网络请求、解析、缓存和工件获取；React 只接收目录 DTO 与任务状态，不绕开 DesktopGateway 直接跑安装命令。
- 每个来源保存类型、地址、分支/路径配置、启用状态、上次成功时间、ETag/Last-Modified（若支持）及错误状态。首版使用少量内置解析器和配置项，不做动态脚本插件框架。
- 默认用户点“刷新”时同步；页面进入时可刷新超过 24 小时的缓存。使用小并发和来源级去重，不做全站定时扫描。
- 按来源 API 的分页、限流和重试提示处理；失败保留上一次成功目录，显示“缓存于……”。授权令牌如确实需要，沿用系统凭据存储，不能与模型 API Key 混用。[S24]
- 来源内容变更解析失败、网络离线、认证不足、请求限流、正常零结果分别呈现；不能都显示“暂无扩展”。支持单个来源重试。
- 统一对象标识至少包含生态、规范来源、包名或仓库子路径。相同来源的镜像可关联，分叉仓库和同名 Skill 不自动合并；版本/ref 单独记录。
- 保存声明的兼容信息、发布时间、许可证链接、作者、依赖和原始来源链接。缺失信息显示未知；不生成虚假下载量、评分或“官方认证”。

#### 4. 安装与就地操作

入口支持“安装到实例”和“加入组合”。如果存在多个实例，明确选择目标；从实例详情进入时预选该实例，不写入用户全局 DSH/Pi 目录。

安装计划需要解释：选择的资源、自动补齐的必需依赖、可选项、冲突项、重复内嵌组件、目标路径和启用方式。版本由 resolver 固定后交给现有 Installer；复用取消、失败保护、日志和底部任务进度，不新增一套市场安装器。

生态适配必须保留差异：

- DSH：读取 bundle 声明，按目标 profile 处理顺序、启用与配置补丁；普通 npm 依赖没有装配声明时不显示“插件已启用”。
- Pi：识别包内 extensions / skills / prompts / themes 和选择规则，按支持能力启用；Pi Web 自身不支持的界面交互直接说明。
- Skills：导入完整目录，包括被引用的脚本和资源；声明能被两种引擎读取不等于所有宿主工具都存在，额外命令与平台要求要保留。

插件可能执行与引擎同权限的代码；使用现有安装计划显示必要的脚本/执行提示。没有隔离能力时不称为“沙盒插件”。不要解析 README 的任意 shell 命令并自动运行，也不要为每个普通文件额外建立审批流程。

支持启用、禁用、移除、查看来源和固定版本更新。发现用户通过原生工作台改动了栖点管理的资源时，先显示实际差异，让用户选择采纳或恢复；不要静默覆盖。无法可靠热加载的资源显示“重启后生效”。

#### 5. 用户添加资源

首版支持：npm 精确包版本、GitHub 仓库/固定 ref/子目录、受支持的 HTTPS 清单或压缩包、本地目录和压缩包。用户输入后先识别类型并预览；无法识别时说明缺少什么，不兜底执行任意安装器。

本地资源默认复制进受管目录并记录摘要，保证实例独立。开发用链接模式可后置，不默认让多个实例共享可变源文件。压缩包解包限制在目标目录内，阻止路径穿越和越界链接；这是导入实现的必要检查，不扩大为独立安全审计项目。

验收：DSH、Pi、Skill 各一项真实外部资源进入目录并安装到指定实例；至少一项包内多类型资源可正确展示；跨生态冲突被拦截；新增来源、刷新、断网缓存和失效来源可解释。无需安装市场所有条目。

### P8.3 — 固定整合包与用户自定义组合

#### 1. 固定整合包的定位

继续提供 P5 已能安装的两个组合，并用它们的真实 lock 作为第一批模板。面向用户的主题优先为“开发者的日常”和“把线索变成答案”；若现有包名称不同，先保留，按真实内容调整文案，不为了主题塞入未经适配的依赖。

精选包详情应让用户知道：适合什么工作、包含什么、使用哪个引擎/Web、需要什么模型能力、占用多少空间、哪些内容可调整。预计下载量只根据实际工件元数据计算，缺失时标明待计算。

每个可执行整合包只绑定一个引擎组合。同一主题如需 DSH / Pi 两种版本，做两个明确的变体；不把两个引擎混装成一个运行实例。后续主题按真实需求补充，不先生产几十个展示包。

#### 2. 创建与编辑流程

提供三个入口：“空白组合”“基于精选包修改”“从已有实例保存”。

1. 选择引擎与 Web 组合，默认使用推荐版本。
2. 从市场或本地加入插件、Skills、提示词、主题和已支持的预设；右侧保留 C 的组合清单，支持移除和查看依赖。
3. 设置名称、说明、封面和可公开的配置。封面沿用现有视觉资产；需要新插画且可调用 ChatGPT image 模型时优先使用，不先投入图像编辑器开发。
4. 即时展示冲突和必需项；切换引擎后标出不再兼容的资源，保留用户选择，避免静默清空。
5. 保存为草稿，或解析并锁定成可安装 revision，再选择“创建实例”。未满足条件的草稿可继续编辑，但不能显示为已可安装。

编辑已有包生成新 revision；不会修改已经由旧版本创建的实例。实例详情可提示“组合有新版本”，点击后复用版本差异与更新流程。未保存编辑在离开时保留草稿或提示处理。

“从实例保存”只提取受管组件与允许公开的配置，遇到手工添加、无法追溯来源的资源要标注缺口。用户可补充来源或作为允许分发的本地资源打包，不能导出一个看似完整却无法重建的组合。

#### 3. 组合清单与锁文件

继续使用现有 manifest / lock 格式并增加 `schemaVersion` 迁移；不要另立一套与 P5/P6 不兼容的安装格式。推荐最小分工：

| 内容 | 应保存的字段 |
| --- | --- |
| 整合包 manifest | 稳定 ID、名称、简介、引擎/Web 选择、资源选择、允许的配置、模型协议/能力需求、可公开封面与来源说明。 |
| 整合包 lock | 精确引擎/Web/运行时、包版本或提交、包内选择、依赖解析结果、工件来源和完整性值、适配配置版本。 |
| 本机草稿状态 | 编辑位置、未解析项、当前 UI 选择；不作为跨机器执行依据。 |
| 实例本地绑定 | `connectionId`、项目目录及本机数据路径；只存在实例本地，不进入分享清单。 |

同名文件、同一预设键、重叠配置和重复资源需要显式合并规则；默认指出冲突，允许选择保留哪项。DSH 的装配顺序作为顺序字段保存，Pi 的资源选择保留原有语义，不能一律按“最后一个覆盖”处理。

不允许分享包定义任意启动 shell 或覆盖整个全局配置目录；需要安装操作的内容走既有适配器。外部来源无法固定到可复现版本时，保留为草稿或说明限制，不能宣称已锁定。

#### 4. 导入、导出与模型连接

- 首版分享方式为本地文件：沿用清单导出，并在确有本地静态资源时支持包含 manifest、lock、允许分发资源的压缩包。远程资源优先保留来源引用，无需默认重新托管所有插件。
- 导出使用字段白名单：不含 API Key、auth 文件、会话、日志、机器绝对路径和本机连接 ID。自定义服务商地址等私有配置默认转换为待绑定需求，不直接附带。
- 本机克隆仍沿用连接引用。跨机器导入时，自动列出已有兼容连接，用户选择即可；有默认兼容连接时可预选。只有本机没有合适连接才引导新增一次，**不要求每个实例重新填 API**。
- 导入先显示内容、来源和兼容情况，再创建实例；未知 schema 不强行解释。离线可读取清单和缓存，缺工件时明确列出，不能把导入成功等同于安装成功。
- “导出分享包”与“实例快照备份”是不同动作；本阶段不改变现有快照对受管数据的恢复语义。

验收：由固定包修改一个自定义组合，保存后重新打开继续编辑；导出并在新实例目录重建；目标实例复用已有模型连接；原包、原实例与其共享 Key 均不被修改。

### P8.4 — 最小架构增量与开发顺序

先阅读当前实现，按职责落到已有模块。下面是逻辑职责名称，不要求原样创建新服务、全新目录或第二套数据库。

| 职责 | 负责什么 | 复用边界 |
| --- | --- | --- |
| SourceRegistry / SourceAdapter | 来源配置、目录拉取、元数据规范化、来源状态 | 使用现有网络、SQLite、缓存与凭据能力；不执行安装。 |
| Catalog / VersionResolver | 统一检索、版本合并、兼容判定、精确依赖计划 | 复用 profile 与 lock；不管理进程。 |
| EngineAdapter | DSH/Pi 的配置、装配与工作台差异 | 扩充已有适配器；不各自复制 Installer/Supervisor。 |
| PackService | 组合草稿、revision、导入导出与从实例提取 | 复用 P5 包模型和 P6 更新事务。 |
| DesktopGateway / React | 目录、详情、编辑交互及任务反馈 | 保持当前页面和全局状态栏，调用已有命令边界。 |

必要数据增量限于来源配置/同步状态、目录条目/版本缓存、兼容规则和组合草稿/revision。字段根据现有 schema 合并，不为了本文表格重建数据库。只读目录与下载工件分开缓存；缓存清理继续尊重实例、lock 和快照的引用。

按以下切片顺序提交，每一项留下可点击或可运行结果：

### P8.5 — 有限验收与完成标准

项目为个人开源研发，采用针对本次变更的必要验证，不建设全版本、全资源、全平台测试矩阵。优先复用已有检查与手动冒烟；涉及解析/导入边界或已有 bug 时补少量有价值的测试，纯文案和简单布局不单独加测试。

最终只需覆盖以下代表性结果，实施过程中已经取得的证据可复用，不在阶段末整套重复：

1. 双引擎版本目录有真实数据、历史/预览筛选与可解释的兼容状态。
2. 一个非默认组合真实创建或切换成功，一次失败路径保留原实例。
3. DSH、Pi、Skill 各一项外部资源安装到正确实例，多类型包没有被错误拆装。
4. 一处明确的依赖/宿主冲突可阻止错误计划，不以运行报错代替全部判断。
5. 自定义整合包完成编辑、锁定、导出、导入与实例创建，共享模型连接继续可用。
6. 一次离线/来源失败能回退到已有目录，导出内容不含私密字段，现有 B 布局和底部状态栏仍可操作。

模型调用不用于版本目录、抓取和安装的常规验证；不批量消耗用户额度。确有连接适配变化时再针对对应情况验证。已有测试/构建若覆盖本次改动则按仓库要求运行，未运行项目如实说明，不以补齐 P0–P7 历史检查作为 P8 完成条件。

只更新本计划、必要的代码注释和已有 `PROGRESS.md` 的简短进展；只有用户可见用法改变时更新相应 README。不要另建每个切片的设计说明、测试报告和重复进度文件。
